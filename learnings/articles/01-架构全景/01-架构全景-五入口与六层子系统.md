Hermes Agent 不从单一入口启动。它提供了**五种入口方式**，每种面向不同的使用场景，但它们共享同一个**六层内核子系统**：

### 核心设计原则

从架构全景中，可以提炼三条贯穿 Hermes 始终的设计原则：

1. **单一内核，多态入口**：`AIAgent` 类是所有入口的共享内核。CLI 用它做交互、Gateway 用它回消息、ACP 用它响应 IDE、Batch Runner 用它生成轨迹、API Server 用它处理 REST 请求。五个入口只是不同的 I/O 适配层，核心逻辑不变。

2. **六层管道，层层解耦**：Prompt Builder → Provider Resolution → Tool Dispatch → Context Compression → Memory Management → Session Persistence。每层有独立职责和接口，可以独立替换或增强（例如 Memory Provider 可插拔）。

3. **同步模型，异步适配**：`AIAgent.run_conversation()` 是纯同步的，返回最终结果后才结束。CLI 和 Gateway 在各自的 I/O 层做异步适配——Gateway 用 `asyncio.create_task()` 包同步循环，ACP 用 `asyncio.to_thread()` 桥接。

## 一、五入口全景

### 1.1 CLI 入口 —— 交互式终端

CLI 是 Hermes 最直观的入口。用户执行 `hermes` 启动交互式会话，`HermesCLI` 处理输入、调用 `AIAgent`、渲染输出。

**启动链路**：

```
hermes (命令行)
  → hermes_cli/main.py:main()
    → 解析子命令（默认启动交互式会话）
    → 构造 HermesCLI 实例
      → 加载配置（~/.hermes/config.yaml）
      → 解析 Provider + Model
      → 创建 AIAgent 实例
      → 进入 read-eval-print 循环
```

关键代码路径：

```python
# hermes_cli/main.py — CLI 入口（简化）
def main():
    # 1. 解析子命令（默认：交互式 REPL）
    args = parser.parse_args()
    # 2. HermesCLI 负责会话生命周期
    cli = HermesCLI(args)
    # 3. 内部创建 AIAgent → 进入 REPL 循环
    cli.run()
```

HermesCLI 不只是简单的输入输出循环，它负责：
- **命令解析**：`/model`、`/skills`、`/memory`、`/tools` 等斜杠命令
- **皮肤引擎**：终端主题定制（`skin_engine.py`）
- **认证管理**：Provider 凭据的第一次引导和持久化
- **配置迁移**：检测旧版配置并自动迁移

### 1.2 Gateway 入口 —— 多平台消息网关

Gateway 是一个**长驻进程**，启动后同时连接 Telegram、Discord、Slack、WhatsApp、微信、飞书等 20 个消息平台。它自己是一个独立的 Python 进程，内部维护一个 `asyncio` 事件循环。

**启动链路**：

```
hermes gateway start
  → gateway/run.py:main()
    → asyncio.run(start_gateway(config))
      → 加载 GatewayConfig（平台列表、凭据、端口）
      → 遍历配置的 platform adapters
        → adapter.start() → 建立 WebSocket/长轮询/Webhook
      → 事件循环等待平台消息
        → 收到消息 → _handle_message()
          → 创建 AIAgent（注入会话历史）
          → AIAgent.run_conversation()
          → 通过 adapter 发送回复
```

Gateway 的独特设计在于：
- **platform adapter 模式**：每个消息平台是一个 adapter 类，实现 `on_message()` 和 `send_message()` 接口
- **会话保持**：通过 `gateway/session.py` 的 `SessionStore` 跨会话保持对话历史
- **Cron 集成**：Gateway 内置 `cron/` 定时任务调度器，支持定时执行的 Agent 任务
- **Curator 调度**：Hermes 的自主知识管家（Curator）由 Gateway 的 cron ticker 触发

### 1.3 ACP 入口 —— 编辑器集成

ACP（Agent Communication Protocol）入口让 Hermes 作为编辑器内的 AI Coding Agent 运行——VS Code、Zed、JetBrains 通过 stdio JSON-RPC 与 Hermes 通信。

**启动链路**：

```
hermes acp / hermes-acp / python -m acp_adapter
  → acp_adapter/entry.py:main()
    → 加载 ~/.hermes/.env
    → 构造 HermesACPAgent
    → acp.run_agent(agent, use_unstable_protocol=True)
      → stdout 走 JSON-RPC（ACP 协议传输）
      → stderr 走日志
```

ACP 模式的特殊性：
- **受限工具集**：使用 `hermes-acp` 工具集，排除消息投递和 cron 管理等非编辑器工具
- **cwd 绑定**：将编辑器的当前工作目录映射为 Hermes 的执行目录
- **审批简化**：危险命令的审批走编辑器内弹窗（allow once / allow always / deny）
- **流式渲染**：思考过程、工具调用、文件 diff 作为流式事件发送给编辑器

### 1.4 Batch Runner —— 并行批处理

Batch Runner 用于**大规模轨迹生成**（RL 训练数据）和**批量评估**。它基于 Python `multiprocessing.Pool` 做并行，每个子进程独立创建一个 `AIAgent` 实例。

```
python batch_runner.py --dataset_file=data.jsonl --batch_size=10 --run_name=my_run
  → 加载 dataset（JSONL）
  → 按 batch_size 分片
  → multiprocessing.Pool.map → 每个 worker 执行一条 prompt
    → 创建 AIAgent（skip_context_files=True）→ run_conversation()
    → 保存 trajectory（JSONL）
    → 保存 checkpoint（支持 resume）
```

关键设计：
- **checkpoint 容错**：中断后可 resume，从已完成的 prompt 继续
- **多种工具集分布**：支持 `--distribution=image_gen` 等，控制工具抽样策略
- **轨迹格式**：输出 `from/value` 格式的 trajectory，可直接用于 RL 训练

### 1.5 API Server —— REST 接口

API Server 是 Gateway 的一个特殊 platform adapter（`api_server`），将 Hermes 的能力暴露为 RESTful API。它与 Gateway 共享同一进程，通过 HTTP 端点接收请求。

```
POST /api/v1/chat
  → Gateway platform adapter (api_server)
    → 创建 AIAgent
    → run_conversation()
    → 返回 JSON 响应
```

### 1.6 五入口对比

![五入口对比矩阵 — 场景、隔离、并发、工具集](./diagrams/all-diagrams.html)

| 维度 | CLI | Gateway | ACP | Batch Runner | API Server |
|------|-----|---------|-----|-------------|------------|
| **使用场景** | 交互式开发 | 多平台客服/自动化 | 编辑器 Coding Agent | RL 训练数据生成 | 系统集成 |
| **进程模型** | 前台交互 | `asyncio` 长驻 | stdio 子进程 | `multiprocessing` | Gateway 子模块 |

| **工具集** | 全量 | 全量 | `hermes-acp` 精选 | 按分布抽样 | 可配置 |
| **会话保持** | SessionDB | SessionStore | 内存（进程级） | 无 | SessionStore |
| **Context Files** | 加载 | 加载 | 加载 | skip | 加载 |

## 二、六层内核子系统

从 `AIAgent.__init__()` 的参数和初始化流程中，可以清晰看到六层内核的组装过程：

### 2.1 第 1 层：Prompt Builder —— 系统提示词组装

`prompt_builder.py` 负责将多种信息源拼装成最终的 System Prompt。输入包括：

| 来源 | 说明 | 管理方式 |
|------|------|---------|
| `SOUL.md` | Agent 身份和个性 | 用户编辑 |
| `AGENTS.md` | 项目级指令 | 项目目录 |
| **Context Files** | MEMORY.md / USER.md | MemoryStore |
| **Platform Hints** | 平台格式化提示（CLI/Gateway） | 平台注入 |
| **Skill Content** | 激活的 Skill 文档 | Skill 系统 |
| **Memory Context** | Provider 返回的记忆上下文 | MemoryManager |
| **Ephemeral Prompt** | 运行时注入的临时提示 | API 参数 |

组装顺序是固定的——先是身份（SOUL.md），然后是项目指令（AGENTS.md），接着是知识（Memory/Skill），最后是运行时注入。这个顺序保证了**声明性知识不会覆盖身份定义**。

### 2.2 第 2 层：Provider Resolution —— 模型与 API 路由

`runtime_provider.py` 负责回答一个问题：**用哪个模型，走哪种 API 格式？**

Hermes 支持 30+ Provider，使用三种 API 模式：

| API 模式 | 适用 Provider | 特点 |
|---------|-------------|------|
| `chat_completions` | OpenAI / Together / Groq / DeepSeek / OpenRouter 等 | OpenAI-compatible，最广泛 |
| `codex_responses` | OpenAI Codex / xAI | Codex 的原生 responses endpoint |
| `anthropic_messages` | Anthropic / Bedrock / Vertex | Anthropic 原生 Messages API + Prompt Cache |
| `bedrock_converse` | AWS Bedrock Converse | Bedrock 统一 API |

Provider 解析遵循优先级链：配置文件 → 环境变量 → 自动探测。同一 Provider 可能有多种 API 模式（例如 Anthropic 可以走 `anthropic_messages` 也可以走 OpenRouter 的 `chat_completions` 代理），选择逻辑在 `runtime_provider.py` 中。

### 2.3 第 3 层：Tool Dispatch —— 工具发现与分发

`model_tools.py`（~1000 行）是工具系统的调度中心。它的核心职责：

1. **工具发现**：扫描 `tools/registry.py` 注册的 61 个工具
2. **Schema 收集**：为每个工具生成 OpenAI Function Calling 格式的 JSON Schema
3. **分发执行**：解析模型返回的 `tool_call` → 查找工具 → 执行 → 返回结果
4. **MCP 集成**：动态发现 MCP 服务器的工具
5. **工具集过滤**：根据入口类型过滤可用工具（`enabled_toolsets` / `disabled_toolsets`）

```python
# model_tools.py — 工具分发核心逻辑（简化）
def handle_function_call(self, tool_calls, messages):
    for tc in tool_calls:
        tool_name = tc["function"]["name"]
        tool_args = json.loads(tc["function"]["arguments"])

        # 1. 查找工具
        tool_fn = self.tools[tool_name]

        # 2. 安全检查（approval.py）
        if is_dangerous(tool_name, tool_args):
            # 走审批流程（CLI 交互 / Gateway 回调 / ACP 弹窗）
            ...

        # 3. 执行工具
        result = tool_fn(**tool_args)

        # 4. 结果回传给模型
        messages.append({"role": "tool", "content": result})
```

### 2.4 第 4 层：Context Compression —— 上下文智能压缩

当对话历史超过模型上下文窗口时，`context_compressor.py` 介入。它使用**损失摘要策略**：

```
对话历史过长 → 触发压缩
  → 1. 用主模型对历史做摘要
  → 2. 主模型失败？→ 切换到 fallback 模型重试
  → 3. fallback 也失败？→ 纯截断（保留最近 N 轮）
```

压缩后的摘要以 `<conversation-history-summary>` 标签注入系统提示词，完整历史被清除。这是一种**单向压缩**——压缩后不可逆，摘要质量直接决定后续对话质量。

### 2.5 第 5 层：Memory Management —— 双层记忆编排

`memory_manager.py` 是记忆系统的编排器，管理 Built-in Memory（MEMORY.md / USER.md）和 External Provider（Honcho / Mem0 / Supermemory 等）。

编排模式是 **"广播 + 容错隔离"**：

```
每轮对话前：
  1. prefetch_all() → 向所有 Provider 广播 prefetch → 合并结果

每轮对话后：
  2. sync_turn() → 向所有 Provider 广播本轮对话内容

工具调用时：
  3. 将 Provider 工具 Schema 注入 System Prompt
  4. 模型可以主动调用记忆工具（如 memory_search、user_profile 等）
```

关键特性：**单个 Provider 故障不阻塞**。每个 Provider 的调用被 try/except 包裹，失败只记录日志，继续下一个。这保证了即使 Honcho 服务器宕机，Agent 仍然可以正常工作（只是缺少智能记忆功能）。

### 2.6 第 6 层：Session Persistence —— 会话持久化

`hermes_state.py` 基于 SQLite + FTS5 全文搜索实现会话持久化。它记录的不仅是对话历史，还包括：

- **终端输出**：每个工具调用的 stdout/stderr
- **文件操作**：read_file / write_file / patch 的完整路径和内容摘要
- **工具使用统计**：每个工具的使用次数和平均耗时
- **模型参数**：每轮使用的 model / provider / api_mode
- **时间戳**：每轮对话的精确时间

SessionDB 的设计目标是**完整的会话可审计性**——任何时候都可以回溯"这个 Agent 在某月某日做了什么操作、用了什么工具、产生了什么输出"。

支持的操作：
- `search()`：FTS5 全文搜索（跨所有历史会话）
- `fork()`：从历史会话的某个点创建分支
- `export()`：导出为可读格式
- `session list`：列出所有历史会话

## 三、配置层级

![Hermes 配置层级 — 四层覆盖关系](./diagrams/all-diagrams.html)

Hermes 的配置使用**四层覆盖模型**，从最通用到最具体：

```
Layer 1: 默认值（hermes_cli/config.py: DEFAULT_CONFIG）
       │  内置的全局默认配置
       │
       ▼
Layer 2: ~/.hermes/config.yaml
       │  用户级覆盖（适用于所有会话）
       │
       ▼
Layer 3: .env / 环境变量
       │  运行时覆盖（适用于当前进程）
       │
       ▼
Layer 4: CLI 参数 / API 参数
       │  调用级覆盖（仅本次会话）
       │
       ▼
  最终有效配置
```

配置迁移由 `hermes_cli/config.py` 的 `migrate_config()` 函数处理，自动检测旧版配置格式并升级。

## 四、对标分析

### 4.1 与 Gemini CLI 对比

| 维度 | Hermes | Gemini CLI |
|------|--------|-----------|
| **入口数量** | 5（CLI/Gateway/ACP/Batch/API） | 2（CLI + IDE Extension） |
| **消息平台** | 20 平台 Gateway（Telegram/Discord/Slack/微信/飞书等） | 无 |
| **编辑器集成** | ACP 协议（VS Code/Zed/JetBrains） | 自有 extension |
| **Batch Runner** | multiprocessing 并行 + checkpoint resume | 无独立 batch runner |
| **进程模型** | 同步 AIAgent + 异步适配层 | 全异步（TypeScript runtime） |
| **配置层级** | 四层覆盖（默认→config.yaml→env→CLI参数） | 三层（Global→Extension→Project） |
| **内核层数** | 六层显式管道 | 四阶段循环（Map→Route→Execute→Iterate） |

**关键差异**：Hermes 的多入口设计是其最大差异点——它不只是开发者的 CLI 工具，也是可以部署在服务器上的**自主 Agent 运行时**（Gateway 长驻 + Cron 定时任务 + Curator 知识维护）。Gemini CLI 更纯粹地聚焦在开发者的命令行交互场景。

### 4.2 与 Claude Code 对比

| 维度 | Hermes | Claude Code |
|------|--------|-------------|
| **入口数量** | 5（CLI/Gateway/ACP/Batch/API） | 1（CLI） |
| **消息平台** | 20 平台 Gateway | 无 |
| **编辑器集成** | ACP 协议（开放标准） | VS Code / JetBrains 专用 plugin |
| **Batch Runner** | 有（RL 训练数据生成） | 无（claude --print 可管道化但不是 batch runner） |
| **进程模型** | 同步循环 + 异步适配 | async generator（`query.ts`） |
| **会话持久化** | SQLite + FTS5（跨会话历史搜索） | 文件系统（session JSONL） |
| **API Server** | 有（REST 端点） | 无 |

**关键差异**：Claude Code 的设计哲学是"一个强大的 CLI 工具"，Hermes 的设计哲学是"一个可以部署的 Agent 运行时平台"。Gateway + Cron + API Server 的组合让 Hermes 可以作为一个**后台服务**持续运行，而不仅仅是开发者的终端助手。

## 五、设计哲学提炼

纵观 Hermes 的架构全景，可以提炼三条可迁移的架构命题：

**命题一：多入口不是代码复制，而是 I/O 适配层的组合。** CLI/Gateway/ACP/Batch/API 五种入口共享同一个 `AIAgent` 内核，差异化仅在于输入来源（stdin/消息事件/JSON-RPC/dataset/HTTP）和输出方式（终端渲染/平台回复/流式事件/文件写入/JSON 响应）。这证明了"单一内核 + 多态入口"模式对 Agent 系统的适用性。

**命题二：内核设计应遵循"管道化而非单体化"。** Prompt Builder → Provider Resolution → Tool Dispatch → Compression → Memory → Persistence 六层各司其职。新增一个 Memory Provider 不需要改动 Tool Dispatch，新增一个 API 模式不需要改动 Prompt Builder。层间接口清晰，迭代可以发生在单层内部。

**命题三：配置系统应有明确的覆盖语义。** 默认值 → config.yaml → env → CLI 参数四层覆盖模型保证了"任何设置都可以被任何层级覆盖"，同时不会产生歧义——后一层总是覆盖前一层。
