## 架构总览

当 Agent 与模型持续对话，历史消息量不可避免地超过上下文窗口。Hermes 的解决方案不是简单地截断——而是一套**带摘要的损失压缩管道**，与 Anthropic Prompt Cache 协同工作。

## 一、触发时机：两种路径

上下文压缩有两个触发路径：

### 1.1 API 错误触发（被动压缩）

当 API 返回 `context_length_exceeded` 错误时，压缩被触发。这是最常见的路径——模型告诉 Hermes "你的历史太长了"。

### 1.2 Preflight 检查（主动压缩）

更巧妙的是，`run_conversation()` 在进入主循环前会做一次**Preflight 检查**：

```python
# run_agent.py — Preflight 压缩检查
_preflight_tokens = estimate_request_tokens_rough(
    messages,
    system_prompt=active_system_prompt or "",
    tools=self.tools or None,  # ← 关键：tool schemas 可能占 20-30K tokens！
)
if _preflight_tokens >= self.context_compressor.threshold_tokens:
    # 压缩 → 最多 3 次尝试
    for _pass in range(3):
        messages, active_system_prompt = self._compress_context(...)
```

这让 Hermes 能在**发请求之前**就主动压缩，避免了提交一个注定失败的请求。阈值默认是上下文长度的 75%。

## 二、压缩策略：保留什么、丢掉什么

压缩器的核心策略是**保护两端、摘要中间**：

| 区域 | 保留策略 | 内容 |
|------|---------|------|
| **头部（head）** | 保留前 3 条消息 | 用户首次输入 + 模型首次回应 |
| **中间（middle）** | LLM 摘要 | 任务进展、关键决策、待解决问题 |
| **尾部（tail）** | token 预算保护（~12,000 tokens） | 最近几轮对话，含完整工具输出 |

### 2.1 Token 预算制的尾部保护

尾部的保留不是固定消息数量，而是基于 **token 预算**：

```python
# context_compressor.py
target_tokens = int(self.threshold_tokens * self.summary_target_ratio)
self.tail_token_budget = target_tokens  # 默认约 12,000 tokens
```

从末尾向前遍历消息，累积 token count，直到达到预算。这样做的优势：
- 大上下文模型（200K）自然保留更多消息
- 小上下文模型（32K）不会因固定数量而溢出
- 不会因某个巨大的工具输出（如 `read_file` 返回 10K tokens）导致尾部截断

### 2.2 边界对齐

压缩边界不能随意切——必须确保：
- 不切在 tool_call 和 tool_result 中间
- 最新的用户消息一定在尾部
- 切点向前搜索到 user/assistant 角色

```python
# 确保当前活跃任务不被丢到中间区域
cut_idx = self._ensure_last_user_message_in_tail(messages, cut_idx, head_end)
```

### 2.3 摘要格式：结构化模板

摘要不是自由文本，而是严格的结构化模板：

```
## Progress
[What has been accomplished so far]

## Key Decisions
[Important technical decisions and WHY]

## Resolved Questions
[Questions that were ALREADY answered]

## Pending User Asks
[Questions NOT yet answered]

## Relevant Files
[Files read, modified, or created]

## Remaining Work
[What remains to be done — framed as context, not instructions]

## Critical Context
[Specific values, error messages, config that would be lost]
```

这是个很好的设计："Remaining Work" 不是"Next Steps"——后者会被模型误读为指令，前者是纯信息上下文。

### 2.4 迭代摘要更新

如果之前已经压缩过一次，后续压缩不会从零开始，而是**在之前的摘要上做迭代更新**：

```
You are updating a context compaction summary.
A previous compaction produced the summary below.
New conversation turns have occurred since then.

PREVIOUS SUMMARY:
{之前的摘要}

NEW TURNS TO INCORPORATE:
{新轮次}

Produce an UPDATED summary...
```

这保留了跨压缩的历史信息。

## 三、降级策略：三级 Fallback

压缩本身也可能失败——模型不可用、超时、服务端错误。Hermes 的三级降级是：

```
Level 1: 用 summary_model (辅助模型) 生成摘要
    ↓ 失败（summary_model 404/503/"model not found"）
Level 2: Fallback 到主模型 (self.model) 重试
    ↓ 失败（transient error: timeout/rate-limit/network）
    ↓ → 60 秒 cooldown，期间跳过所有摘要尝试
Level 3: 纯截断
    中间消息直接丢弃，不插入摘要
    尾部消息保留，头部消息保留
```

关键细节：**permanent error 和 transient error 的处理不同**。Summary model 不存在（404/503/"does not exist"）→ 立即 fallback 到主模型。Transient 错误（timeout/rate-limit）→ 60 秒 cooldown，防止连续重试压垮服务。

## 四、Prompt Cache 管理

### 4.1 缓存策略

Hermes 对 Anthropic 模型使用 **system + 最末 3 条消息** 的缓存断点策略（`system_and_3`），将 system prompt 和最新消息标记为 `cache_control`：

```python
# 自动检测并应用缓存
if self._use_prompt_caching:
    api_messages = apply_anthropic_cache_control(
        api_messages,
        cache_ttl=self._cache_ttl,  # "5m" 或 "1h"
        native_anthropic=self._use_native_cache_layout,
    )
```

### 4.2 缓存失效与重建

压缩会**破坏 Prompt Cache**。因为压缩后 system prompt 和消息列表变了，缓存的 token 前缀不再匹配。Hermes 的处理是：

1. 压缩时 **`session_id` 不变，但 system prompt 重建**
2. 重建后的 system prompt + 新消息列表形成新的 cache key
3. 下一轮 API 调用会建立新的缓存前缀
4. `on_session_switch` 通知 memory provider 会话 ID 变化（压缩创建新 session ID）

### 4.3 缓存 TTL

支持两种 TTL：
- **5m**（默认）：写入成本 1.25x，适合短会话
- **1h**：写入成本 2x，适合长会话（暂停 >5 分钟后仍能命中缓存）

## 五、压缩的副作用与防御

压缩不仅是技术操作，更影响用户体验：

### 5.1 压缩警告与通知

压缩发生时通过 `status_callback` 发通知给 Gateway 平台（Telegram/Discord 等），让用户知道"对话历史被压缩了"。

### 5.2 防抖动（Anti-Thrashing）

如果连续压缩但每次的 token 节省量 <10%（`_last_compression_savings_pct < 10`），`_ineffective_compression_count` 递增。这防止在大块文件操作后反复触发无效压缩。

### 5.3 Memory Provider 的压缩钩子

压缩前调用 `on_pre_compress(messages)`，让 memory provider 能够在消息被丢弃前提取关键信息，注入到摘要提示词中：

```python
# memory_manager.py
def on_pre_compress(self, messages):
    """Notify all providers before context compression."""
    parts = []
    for provider in self._providers:
        result = provider.on_pre_compress(messages)
        if result:
            parts.append(result)
    return "\n\n".join(parts)
```

## 六、对标分析

### 6.1 与 Gemini CLI 对比

| 维度 | Hermes | Gemini CLI |
|------|--------|-----------|
| **触发方式** | Preflight 主动检查 + API 错误被动触发 | 六道递进防线（auto-compact） |
| **压缩策略** | 结构化摘要（8 字段模板） | content-based compaction |
| **降级层次** | 3 级（summary_model → main → truncate） | 多级 |
| **摘要复用** | 迭代更新（保留跨压缩信息） | 每次重建 |
| **Cache 管理** | Anthropic Prompt Cache（显式断点） | Gemini KV Cache（隐式） |

### 6.2 与 Claude Code 对比

| 维度 | Hermes | Claude Code |
|------|--------|-------------|
| **触发方式** | Preflight + API 错误 | Context collapse 检测 |
| **压缩策略** | 结构化摘要（8 字段） | AutoCompact（简化版摘要） |
| **降级与安全** | 三级 fallback + 防抖动 | 单层压缩 |
| **Cache 管理** | system_and_3 策略 + 5m/1h TTL | system_and_N 策略 |

**关键差异**：Hermes 的压缩设计更详尽——8 字段结构化模板、迭代摘要更新、三级 fallback、60s cooldown、防抖动跟踪。Claude Code 的 AutoCompact 更轻量但功能更少。

## 七、设计哲学提炼

**命题一：压缩是信息保留问题，不是消息丢弃问题。** 结构化摘要模板（Progress / Key Decisions / Resolved Questions / Pending User Asks / Relevant Files / Remaining Work / Critical Context）确保压缩后模型仍然拥有完成任务所需的上下文，而不仅仅是"之前发生了什么"的模糊叙述。

**命题二：降级路径应该根据错误类型分化。** 永久性错误（模型不存在）和瞬态错误（超时/限流）应该走不同的处理路径。前者可以立即尝试 fallback，后者需要 cooldown 避免加剧问题。

**命题三：压缩是破坏性操作，需要副作用管理。** 每次压缩触发 memory provider 钩子、通知用户、重建 Prompt Cache、创建新 session。这些副作用不是可选的——它们决定了用户体验的连续性。
