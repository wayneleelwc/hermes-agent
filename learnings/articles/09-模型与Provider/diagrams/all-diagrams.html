核心命题：Hermes 的 Provider 体系设计哲学是"用户只说模型名，系统自动找 key + url + 协议"。四层架构（认证→身份→模型目录→运行时解析）让 109+ Provider 的接入对外部透明。
Provider 体系四层架构
认证层 → 身份层 → 模型目录层 → 运行时解析层
第1层 认证层 — auth.py (~4,700 行)
OAuth Device Code：Nous Portal、MiniMax、Codex、Qwen — 浏览器授权 → auth.json 持久化
API Key Env Vars：Anthropic、OpenRouter、DeepSeek — 多环境变量链查找
外部进程：Copilot ACP、Gemini CLI OAuth — 外部命令获取临时凭证
Token 刷新：access token 到期前 120 秒自动刷新；Nous Portal 使用 30 分钟短效 agent key
第2层 身份层 — providers.py (~700 行)
数据源1：models.dev 动态目录（109+ Provider 完整元数据）→ 缓存到磁盘
数据源2：HermesOverlay 本地补丁（transport / auth_type / extra_env_vars）
数据源3：用户 config.yaml providers: 自定义覆盖
三种传输协议：openai_chat | anthropic_messages | codex_responses
第3层 模型目录层 — models.py (~3,500 行)
_PROVIDER_MODELS：25+ Provider 的静态模型清单
动态拉取：OpenRouter /v1/models、Vercel AI GW /v1/models、Codex 动态列表
models.dev 缓存：xAI 模型从磁盘缓存推导，自动跟踪重命名
第4层 运行时解析层 — runtime_provider.py (~1,300 行)
resolve_runtime_provider() 返回 {provider, api_key, base_url, api_mode}
api_mode 自动检测：api.openai.com → codex_responses、api.minimax.io/anthropic → anthropic_messages

信用耗尽 402 Payment Required fallback
当解析到的 provider 返回 HTTP 402 或 credit 相关错误时，call_llm() 自动切换到 fallback 链中的下一个可用 provider。用户可能感知不到 OpenRouter 余额耗尽——Hermes 自动 fallback 到 Codex OAuth 或 Anthropic API Key。
Codex 排除 有意不在 fallback 链
Codex OAuth 被有意排除在 fallback 链之外。原因：OpenAI 对 Codex 端点实施未公开的、持续变化的模型白名单——"just try Codex with a hardcoded model" 策略会随时间腐化。Codex 仅在用户显式选择为 main provider 时使用。
